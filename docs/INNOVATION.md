# McBuddy AI 创新点说明

> 本文档只描述**已实现**的能力，每个创新点都标注了代码位置以便核验。
> 尚未实现的能力统一列在文末「诚实的局限」一节。

---

## 一句话

**市面上的人格测试绝大多数是「问卷 → 查表 → 输出文案」；
McBuddy 把它做成了一个可计算、可追溯、可复现的六维向量模型。**

---

## 一、起点：这类产品普遍缺什么

麦门/品牌人格测试是一个很拥挤的品类，但翻看同类实现，会发现三个反复出现的问题：

| 问题 | 典型表现 |
|---|---|
| **结果不可追溯** | 给出「你是深夜型人格」，但说不出这个结论由哪一题推出 |
| **实现是查表** | 答案组合直接映射到固定结果，换个答案也只是换一行文案 |
| **不可复现** | 依赖大模型生成，同样输入两次得到的描述不一样 |

McBuddy 的三个设计决策，正是分别对着这三点去的。

---

## 二、创新点

### 创新点 1｜六维向量模型：一题恰好驱动一维

**是什么**：六道情景题对应六个独立维度（快乐需求 / 消费态度 / 口味偏好 / 冒险程度 /
社交属性 / 恢复方式），每题的选项**直接携带该维度的取值**（0–1），而不是增量累加。

**为什么这么做**：如果用「多题叠加 + 归一化」，一旦某个维度被多题共同影响，
结果就再也说不清"这个分数从哪来"。一题一维之后，雷达图上每一个数字都能追溯到具体某道题。

**代码位置**：`frontend/data/questions.ts`（题目与维度映射）、`frontend/lib/scoring.ts` 的 `buildVector()`

**可验证**：结果页会显示「最突出的一维：恢复方式 90%」，这个数字直接来自第 6 题的选择。

---

### 创新点 2｜中心化余弦相似度：一个不显然但必要的技术选择

**是什么**：用**中心化后**的余弦相似度（等价于 Pearson 相关系数）做人格匹配，
而不是普通余弦相似度。

**为什么这么做**——这是整个项目里含金量最高的一个技术判断：

所有六维向量都落在 `[0,1]⁶` 的**正象限**内。在这种数据上，普通余弦相似度的夹角天然很小，
**任意两个人格原型之间的相似度都会超过 0.9**，八种人格根本无法区分——
匹配结果会退化成"几乎随机"。

把每一维减去中位值 0.5 之后，向量被搬到以原点为中心的坐标系，区分度立刻拉开。
这一步不改变任何产品语义，却决定了算法是否真正可用。

**代码位置**：`frontend/lib/scoring.ts` 的 `centeredCosine()`

**可验证**：`frontend/scripts/verify-personas.ts` 会穷举全部 6144 组作答并打印命中分布——
若换成普通余弦，这个脚本会显示所有作答挤在极少数人格上。

---

### 创新点 3｜混合型人格，且阈值由数据标定而非拍脑袋

**是什么**：当 Top1 与 Top2 人格的相似度差距小于阈值时，判定为**混合型**（双人格），
如「🍟 黄金薯条治愈者 × 🧑‍💻 深夜代码战士」。

**为什么这么做**：混合型是传播放大器——「我测出来和别人不一样」比单一标签更有晒图欲。
但阈值不能随便定，否则会泛滥成灾。

**阈值是穷举 6144 组作答后标定的**：

| 阈值 | 混合型占比 | 判断 |
|---|---|---|
| 0.05 | 40.2% | 四成人都是双人格，"我有一个身份"的感觉被稀释 |
| **0.02** | **17.9%** | ✅ 采用，约 1/5.5，既有特别感又不常见 |
| 0.01 | 9.5% | 过于稀有，多数人体验不到 |

**代码位置**：`frontend/lib/scoring.ts` 的 `MIXED_THRESHOLD`（注释中保留了完整标定依据）

---

### 创新点 4｜溢出机制：让画像有层次，但不破坏可追溯性

**是什么**：选项除主维度外可对相邻维度产生次级影响。例如选「🍦 甜品」，
除口味维度外还会拉高恢复方式维度。

**为什么这么做**：纯一题一维会让六个数显得孤立（现实中「爱甜的人往往也靠甜食回血」）。
但溢出如果处理不当，会重新引入"分数说不清来源"的问题。

**解法**：溢出**统一在主维度赋值之后**施加，融合权重固定 0.35，
保证结果与选项遍历顺序无关（可复现）。

**代码位置**：`frontend/lib/scoring.ts` 的 `buildVector()` 第二段

---

### 创新点 5｜确定性结果路径：刻意不让 LLM 参与判定

**是什么**：人格结果由**确定性算法**得出——同样的作答永远得到同样的人格、同样的向量、同样的置信度。
LLM 不参与结果路径。

**为什么这么做**：这看起来像"少用了 AI"，但恰恰是产品判断。
人格测试的信任基础是**可复现**：如果两次测同一套答案得到不同结果，产品立刻失去可信度。
而 `/analysis` 页那段"AI 正在认识你的麦门灵魂"的四步动画，是**纯视觉仪式感**，
不承担任何计算职责——我们不会用动画时长来暗示某种并不存在的"思考"。

**代码位置**：`frontend/lib/scoring.ts`（纯函数，无副作用、无随机数）；
`frontend/components/AnalysisAnimation.tsx`（仅计时与回调）

---

### 创新点 6｜人格主题派生：8 套视觉，零数据改动

**是什么**：八种人格各自拥有专属配色（背景光晕 / 卡片渐变 / 描边 / 海报），
但人格数据结构里**只有三个颜色值**，其余全部由 `themeOf()` 派生。

**为什么这么做**：如果为了让八种人格"看起来不一样"而给数据结构加七八个视觉字段，
数据与表现就会耦合，改一次配色要动八条数据。派生方案把映射规则收敛到一个函数里。

**代码位置**：`frontend/lib/theme.ts`

**附带解决的一个真实问题**：八种人格的渐变里既有高亮黄 `#FFC72C` 也有深蓝 `#0B4F8A`，
白字直接压在整块渐变上，在黄色人格上对比度会严重不足。
因此**结果页卡片**采用「渐变带 + 深色正文区」，而**分享海报**采用「全幅渐变 + 自下而上暗色蒙版」——
同一套人格数据，两种配色策略，分别服务"列表可读"与"发布冲击"两个不同场景。

---

### 创新点 7｜工程创新：零依赖 Demo

**是什么**：访客只需 Python，双击一个文件就能跑起完整产品。

**为什么这是个真问题**：创新大赛的作品，评委很可能只有 3 分钟耐心。
任何一步环境准备失败（装 Node、申请 Token、配 API Key、跑数据库迁移）都会直接损失转化。
因此：

| 决策 | 收益 |
|---|---|
| 前端静态导出 + **产物入库** | 访客**不需要 Node.js** |
| 后端单进程 + 静态托管 | **一个端口**，无跨域、无反向代理 |
| 启动逻辑放 Python，批处理只留 ASCII 外壳 | 规避 cmd.exe 对多字节字符**错切行**的固有缺陷 |
| 轮询 `/health` 而非固定延时 | 慢机器上不会打开"无法连接"的页面 |

**代码位置**：`start.bat` + `scripts/launch.py` + `frontend/next.config.mjs`

## 三、与同类方案的差异

| 维度 | 同类常见做法 | McBuddy |
|---|---|---|
| 结果来源 | 答案组合查表 | 六维向量 + 相似度匹配 |
| 可追溯性 | 无法解释 | 每一维可对应到具体某题 |
| 可复现性 | 依赖 LLM，次次不同 | 确定性算法，完全相同 |
| 人格数量 | 固定单一结果 | 8 型 + 混合型（17.9%） |
| 人群统计 | 常出现无出处的"仅 3% 的人" | **不伪造统计**，只输出行为强度 |
| 视觉 | 一套配色套所有结果 | 8 套主题派生，结果页背景随人格变化 |
| 运行门槛 | 需装依赖 / 申请 Key | 双击即用，零 Token 零 Key |
| 分享物 | 文本或截图 | 3:4 海报 + 一键导出 3 倍像素 PNG |

## 四、一个刻意的克制：不伪造人群统计

很多同类产品会给出「全国仅 3% 的人是这种人格」这类话术。**本项目不做这件事**——
在没有真实样本的情况下编造百分比，既不诚实，也违反赛事对真实性的要求。

替代方案是把"稀有度"换成**可验证的行为强度**：
结果页展示的是「最突出的一维：恢复方式 90%」，这个数字来自你自己的作答，可追溯、可复现。

> 同理，验证脚本打印的人格分布（6.4%–21.2%）是**对本算法 6144 种作答组合的穷举结果**，
> 不是对人群的抽样统计，文档中也如实标注。

## 五、MCP 接入：从「认识你」到「替你做事」

**本项目已真实接入麦当劳 MCP**（Streamable HTTP + Bearer 鉴权），
并已用真实 Token 验证：握手成功、服务端提供 35 个工具、
`list-nutrition-foods` 取到 160 条真实营养数据、`query-nearby-stores` 解析到真实门店。

| 能力 | 依赖的 MCP 工具 | 状态 |
|---|---|---|
| 门店解析 | `query-nearby-stores` | ✅ 已验证 |
| 营养数据 | `list-nutrition-foods` | ✅ 已验证（160 条） |
| 实时菜单 | `query-meals` | ⚠️ 依赖门店营业时段 |
| 真实优惠 | `query-store-coupons` | ✅ 已验证（无券时返回空列表） |
| **真实计价** | `calculate-price` | 🔜 待营业时段内复测 |
| 当期活动 | `campaign-calendar` | ✅ 已验证 |
| 历史订单 | `order-list` | 🔜 未接入（可用真实行为反哺人格） |

### 一个刻意的工程约束：降级必须诚实

真实 MCP 会因**门店打烊、限流、网络异常**而不可用。本项目的处理原则是：

> **宁可显示演示数据，也绝不把 Mock 谎报成实时数据。**

实现方式是在三层都保留 `source` 标记：接口响应、Adapter 内部状态、前端徽标。
门店打烊时实测结果为 `source = "mock"` + 12 条演示菜单，页面照常可用且标注清晰。

完整说明见 [`../MCP_INTEGRATION.md`](../MCP_INTEGRATION.md)。

## 六、诚实的局限

| # | 局限 |
|---|---|
| 1 | 真实菜单受门店营业时段限制，打烊时会降级为演示数据 |
| 2 | `calculate-price` 尚未端到端验证（依赖真实菜单编码） |
| 3 | 无 LLM，因此也没有对话能力 |
| 4 | 无服务端记忆，档案数据为 Mock，状态仅存于本地浏览器 |
| 5 | 人格分布不完全均匀（6.4%–21.2%），这是题目设计的客观结果 |
| 6 | 视觉与 PNG 导出尚未经真机浏览器逐项走查 |

我们选择把这些边界写进文档，而不是用模糊措辞掩盖——**评委看到的能力边界，
应当与运行代码后看到的完全一致。**
